# Qiriness Customer Support OS

A customer-support operating system for **Qiriness**, a French skincare and cosmetics brand: an agentic email reply workflow plus a dashboard, modelled on [letterbook.ai](https://www.letterbook.ai/). Shopify is the source of truth; Supabase/PostgreSQL is the operational database.

Repository map and data model: `APP_SCHEMA.md`. What is built but not yet proven against real data: `VALIDATION_LOG.md`. Coding rules: `AGENTS.md`. Design direction: `PRODUCT.md`. Agent workflow phases: `AGENT_INTEGRATION_PLAN.md`.

## Scope

Built or in progress: one-way Shopify -> Supabase sync, a curated knowledge library for AI context, retrieval embeddings, and email ingestion into conversation-threaded tickets.

Planned: order tracking, delivery issues, returns/refunds, product and payment questions, product advice, complaints and cosmetovigilance escalation, AI categorisation and reply drafting.

## Architecture

- **Shopify** owns products, variants, customers, orders, fulfilments, refunds, and discounts. Shopify IDs are the external identifiers.
- **Supabase PostgreSQL** (+pgvector) is the operational store. Sync is Shopify -> Supabase only, combining an initial import, webhooks for near-real-time updates, and scheduled reconciliation to catch drift. Webhook signature validation and idempotent processing are required. Webhook routes are **not deployed yet**; sync runs as manual/nightly CLI scripts.
- Important Shopify fields go in structured columns; raw payloads are retained only where useful and sanitised of unnecessary personal data.
- French text destined for AI context is normalised for UTF-8/Windows-1252 mojibake before storage, with raw payloads kept for traceability.
- Customer personal data is minimised, hashed where it is only a lookup key, and excluded from AI prompts unless strictly required. AI workflows retrieve context progressively rather than loading whole records.
- Knowledge articles are a **curated library**: nothing auto-syncs into `knowledge_documents`. Shopify pages and policies are catalogued by name only, and become articles when a team member imports one. See `APP_SCHEMA.md`'s Invariants.

## Stack

Confirmed: Shopify · Supabase · PostgreSQL · Next.js (App Router) + TypeScript + React 18 in `web/` (CSS Modules and design tokens, no UI framework) · Node ESM scripts at the repo root · OpenAI for embeddings and classification · Microsoft Graph for the support mailbox.

Pending: dashboard auth, ORM/DB client for app reads (scripts use `pg` + a Supabase REST client), job scheduling, webhook processing runtime, frontend test framework, deployment tooling.

## Getting started

1. `npm install` at the repo root.
2. Copy `.env.example` to `.env.local` and fill it in. This one repo-root file is the single source of truth for secrets — `web/next.config.mjs` and `agent/src/config.mjs` both load it, so there is no separate `web/.env.local`. Needed: `SHOPIFY_STORE_DOMAIN`, `SHOPIFY_ADMIN_API_ACCESS_TOKEN` (or `SHOPIFY_CLIENT_ID` + `SHOPIFY_CLIENT_SECRET`), `SUPABASE_URL`, `SUPABASE_SECRET_KEY`, `SUPABASE_DB_URL`, `OPENAI_API_KEY`, and the `MS_GRAPH_*` + `SUPPORT_MAILBOX` vars for the agent worker. All server-only — never prefix with `NEXT_PUBLIC_`.
3. Apply the six migration files in `supabase/migrations/` **in order** (`01_core_schema.sql`, `02_spam_filter.sql`, `03_categorisation.sql`, `04_forwarding.sql`, `05_forwarding_retry.sql`, `06_knowledge_retrieval.sql`) with `npm run db:apply:migration`. They are a baseline for an empty database, not idempotent patches — 03 extends tables 01 creates, and 04 depends on the axes 03 constrains.
4. Sync Shopify data. Every script has a `:dry-run` twin — run that first to verify API access and mapping:
   `npm run sync:shopify:products` · `:customers` · `:orders` · `:promotions` · `:content-catalog`, or `npm run sync:shopify:nightly` for all of them in order.
5. `npm run embed:knowledge` to embed approved knowledge chunks (`:dry-run` available).
6. `npm test` runs the root test suite (`node --test`).

Microsoft Graph application permissions: `Mail.Read` for ingestion, plus **`Mail.Send`** for the forwarding pass — the only write the worker makes to Graph. Without it forwarding records every attempt as `failed` (with `ErrorAccessDenied`) rather than failing quietly; ingestion and categorisation are unaffected.

Shopify scopes: `read_discounts` for promotions; `read_content`/`read_online_store_pages` and `read_legal_policies` for the content catalog; `read_themes` for the theme-template content fallback. Missing optional scopes surface as a clear import error rather than silent failure. For Shopify Dev Dashboard apps, leave `SHOPIFY_ADMIN_API_ACCESS_TOKEN` blank and the scripts request a short-lived Admin token from the client ID/secret at runtime.

### Dashboard (`web/`)

`cd web && npm install`, then `npm run dev` and open `http://localhost:3000` (redirects to `/agent-setup`). `npm run build`, `npm run lint`, `npm run typecheck` for checks. Run the root sync scripts at least once first — the Knowledge API looks the shop up by domain and returns a clear 404 until a `shops` row and the `shopify_content_sources` catalog exist.

### Agent worker (`agent/`)

`cd agent && npm install`, then `npm run ingest:once` for a single ingestion pass or `npm start` to poll. Also `npm run blocklist:add -- <email|domain>`, `npm run ingest:reset`, and `npm run forward:dry-run` / `forward:once` to rehearse or run the forwarding pass without a mailbox poll.

Working and verified live against the dev Shopify store and Supabase:

Two-pane knowledge workflow: article library with search, status filters, a 6-slot core-topic checklist and category grouping; a workspace editor with Shopify page/policy import, resync, save/approve/delete, and a dedicated brand-voice workspace. Full state and a11y coverage. "Optimize" is still a local placeholder with no AI behind it.
- **Knowledge API** (`web/app/api/knowledge/*`) — exercised end-to-end through the real browser UI, not just curl: page import, policy import, edit-converts-to-manual (Resync correctly disappears), and delete.
- **Tickets dashboard** (`/tickets`) — the agent's queue made visible: four header cards (open, high priority, level 3, new in 24h/30d) over three collapsible sections — Queue (565), Irrelevant (260) and Closed — each scrolling inside a fixed height. Level tabs, search, category filter and sort apply to the queue. **Every row opens with a traffic-light mood face** read from `tickets.happiness`: green 1-2, amber 3, red 4, and a dashed outline where the categoriser has not scored the ticket yet. Neutral (2) is folded into green rather than amber on purpose — it is the commonest score, and an amber row for every ordinary email would turn the whole column amber and signal nothing. Drawn on the app's own icon grid rather than as a Unicode emoji, which would render as each operator's OS artwork and ignore the palette. **Close ticket** and **Reopen ticket** work end-to-end (`PATCH /api/tickets/:id`); the close/reopen round trip was exercised against the live dev database and the row verified moving between sections in both directions. Every card figure and row count matches a direct Supabase query. Two deliberate substitutions are documented in `APP_SCHEMA.md`: "high priority" reads level 3+4 because nothing writes the `priority` column yet, and the volume windows are rolling rather than calendar so a gap between ingestion runs reads as idle rather than as zero.
- **Tickets close themselves after 21 days of silence, and a reply reopens them.** Built but **not yet run against the backlog** — the dry run reports 239 of 510 inactive tickets would close, 271 held back. Rehearse with `npm run tickets:autoclose:dry-run` from `agent/`, then `npm run tickets:autoclose` to write; the worker also runs the pass at the end of every poll. Two exemptions: **level 4 never auto-closes** (legal threat, hospitalisation or grave danger, where silence is the opposite of resolved — level 3 does close), and **a ticket still queued for the categoriser never auto-closes**, because the categoriser selects on `status = 'open'` and closing one would freeze it as uncategorised for good. 270 tickets are currently in that second group; they become closable as the categoriser drains them at 25 per poll. A customer reply reopens a closed ticket and clears its lifecycle timestamps; our own reply does not. 18 unit tests cover the policy, including the null-level case that a SQL-side filter would have silently spared.
- **Why 171 tickets show as uncategorised.** 163 are simply still in the categoriser's queue (25 per poll, and the corpus was ingested far faster than it drained); 8 were skipped deliberately because the mailbox holds only our own replies on those threads, so there is no customer message to classify. The skip clears the flag on purpose — leaving it set parked those tickets at the front of every oldest-first batch. Ingestion re-raises it if a customer ever writes in.
- **The Irrelevant section reads `spam_audit`, not `tickets`** — dropped mail is never stored as a ticket, so the 260 rows are gate decisions carrying sender, subject and reason but **no body**. "Add as ticket" is therefore rendered disabled: promoting one back requires the agent worker to re-fetch it from Graph, which is not built. Deciding that mechanism is the next step for this surface.
- **Saved changes actually survive a reload.** The dashboard used to show pre-edit values after F5 — approved articles back as `draft`, a saved forwarding address back as blank — while Supabase held the correct data. Next.js patches global `fetch` in Server Components and Route Handlers, and it was storing every Supabase REST response in its Data Cache with a one-year revalidate, keyed on URL, so each page replayed the first body it ever saw. `export const dynamic = "force-dynamic"` does not prevent this; only an explicit `cache: 'no-store'` on the fetch does. Now set on every request in `scripts/lib/supabase-rest-client.mjs` (and on the Shopify admin/theme clients, which the import and resync routes call for the same reason). The option is inert outside Next, so the sync scripts and agent worker are unaffected.
- **Shopify sync scripts** — products/metaobjects, customers, orders, promotions, the unified page+policy content catalog, and nightly orchestration.
- **Email ingestion (agent Phase 1)** — verified against the real `onouailhetas@lap-groupe.com` mailbox (cursor idempotency, delta cursor persisted in `shops.sync_cursors`), then end-to-end against the live `contact@qiriness.com` support inbox: 500 messages -> 125 blocklisted, 27 LLM-filtered, 348 stored as 171 threaded tickets, all categorised with no failures. That run is what surfaced the four ingestion fixes below.
- **Ingestion reads the envelope correctly (found by running it on real mail).** Four defects, none visible on synthetic data:
  - *Direction.* The Inbox is not only inbound — the team's own replies land back in it. 123 of 348 messages were sent by the support address and stored as customer mail, putting Qiriness's own reply at the end of 43% of threads, exactly where the categoriser reads how the customer currently feels. A message from the support mailbox is now `outbound`, is never spam-triaged, and is never classified.
  - *Contact-form identity.* 53% of support mail arrives through the Shopify form, which sends from `mailer@shopify.com` with the customer's real name, address, country and message in the body. 95 tickets shared 2 `requester_email_hash` values, so the join key to `orders.customer_email_hash` was unusable for half the inbox. `contact-form.mjs` now parses those fields; distinct requesters went from 76 to 108 and the worst collision from 73 tickets to 8.
  - *`first_message_at`.* Graph's delta is not chronological, so threads are routinely opened by a later reply. The column was late on 93 of 171 tickets (5 days on average, 24 at worst) and the categoriser queue sorts on it. It now moves backwards as well as forwards.
  - *Queue starvation.* A thread holding only our own replies cannot be classified. It was skipped but left pending, so it sat at the front of an oldest-first batch of 25 forever — 11 such tickets took 11 of every 25 slots on every pass. Skipping now clears the flag, which ingestion re-raises when a customer message arrives.
- **Spam gate pass 1** — the `email_blocklist` check inside the poller; blocking a sender live dropped their 5 messages and purged their stored mail.
- **Spam audit trail** — every gate decision writes a `spam_audit` row (`kept`/`blocked`, which pass decided, and a one-line reason; `unsure` when the classifier had no confident reason, `failed_open` when a keep was only a fail-open). Needed because dropped mail is never stored, so this is its only trace. The write path was exercised against the live table: idempotent re-flush, one-line reason collapsing, and the `unsure` default all confirmed, then the test rows removed.
- **Support taxonomy pinned** — one shared vocabulary in `scripts/lib/support-taxonomy.mjs`: 14 subjects used by *both* knowledge categories and ticket categorisation (so a ticket's subject filters straight into matching knowledge chunks), plus `faq`/`brand_story` as knowledge-only, plus a tickets-only request kind (question/problem/complaint/contact) with a second subject+kind pair for emails spanning two topics. Level is derived from (subject, kind) and the categoriser can only escalate. The rename of the 9 existing articles and 54 chunks ran once against dev; the constraints on both the knowledge and ticket sides are applied and their enforcement verified live.
- **Level 4 means severity, not subject** — reserved for an explicit threat of legal action or public exposure, hospitalisation, or grave injury/danger. No (subject, kind) pair derives it, so it can only arrive as a categoriser escalation read from the email itself, and should be rare. A reported skin reaction is a level 2 `cosmetovigilance` problem (the formulations are natural, so reactions are mild allergies or irritations), and an RGPD request is level 3 human work. The database column comments carry this rule; an earlier version had shipped a subject-implied one, and the correction is applied to dev.
- **Human review set on real mail** — 40 emails randomly sampled from `contact@qiriness.com` (Nov 2025 / Dec 2025 / Jan 2026, 40 of 1,027) sit in `categorisation_review` awaiting hand labelling, after which `npm run review:compare` scores the agent against them. The sampler is read-only on the mailbox (GET only, no ingestion, no delta cursor) and the agent's own labels stay empty until after review, so the labelling is blind.
- **Schema fully applied to dev.** The migrations are now a three-file **baseline** -- `01_core_schema.sql`, `02_spam_filter.sql`, `03_categorisation.sql` -- run in order against an empty database, replacing the 15 numbered files that built dev incrementally (kept in git history). The baseline was verified to reproduce the live dev schema exactly: 384 columns, 147 constraints and 136 indexes, zero differences.

Also verified live, all against the real `contact@qiriness.com` mailbox and the dev Supabase project:

- **Embedding pipeline, built and run end to end.** `text-embedding-3-small` at 1536 dims across two corpora sharing one determinism gate. **Knowledge chunks:** 11 of 54 hold vectors — exactly the chunks of the one `approved` document, the invariant (*a vector iff the parent is approved and not brand-voice*) holding on real data; the blocker on embedding more is content approval, not code. **Ticket messages:** all 351 embedded, by an inline best-effort call at ingestion with `npm run embed:tickets` as the reconciler behind it. Both verified idempotent — a second run over unchanged text embeds nothing — and verified working together: clearing six vectors, the ingest pass refilled three inline and the reconciler swept up the rest. Retrieval sanity-checked by hand: an account login question matches the password-reset FAQ at 0.624, and "commande le 17 mai, montant débité" matches "Ma commande 5669 du 17 mai n'est toujours pas partie" at 0.859 across two different tickets. The category is deliberately *not* embedded — retrieval filters on it first, so it adds a constant to every candidate while diluting the content.
- **`irrelevant` now drops, not just labels.** The classifier could always return `keep | spam | irrelevant`, but only `spam` was dropped — so automated notices, FYI forwards of a payment provider's mail and test messages became tickets someone had to close by hand. Both outcomes still write a `spam_audit` row, so a wrong drop is reviewable and can be promoted back. Guard-railed by a measurement: 17 of the 20 purely internal threads in the mailbox turned out to be *customer work forwarded between colleagues* — relances, tracking numbers, refund decisions — so the prompt states explicitly that internal mail about a customer is not irrelevant. Only 1 ticket in the corpus was genuine ERP coordination.
- **Topic clustering over the embedded inbox** (`npm run cluster:tickets`) — read-only, no model calls. Groups messages *within* a subject by average-link cosine clustering, collapsing near-duplicates first so a resend does not look like demand, and reports each topic with its most representative message plus whether an approved knowledge chunk already answers it. Average-link, not single-link: single-link chains (A~B, B~C) and put 52 of 55 `order` messages in one blob. Threshold 0.68, tuned by eye — French support mail shares so much boilerplate that two unrelated emails already sit near 0.55, so the useful band is narrow. Feeds two decisions: which articles to write, and which threads to promote as curated exemplars.
- **The clustering report counts customer mail only, and reads the whole corpus.** Two faults surfaced once the corpus reached 1111 embedded inbound messages, both invisible at the ~225 it was built on. **It was reading 1000 of them:** PostgREST silently caps a response at `db-max-rows`, so the `limit: 5000` in the loader returned 1000 rows and a 206 with nothing for the caller to notice — `supabaseSelectAll` now pages by the rows actually returned, so it stays correct whatever the cap is set to. **And 30% of "customer demand" was us:** `direction` records which way a message crossed the mailbox, not who wrote it, so 331 messages from our own domain counted as inbound and dominated the topics — five of the top ten `delivery` clusters were staff chasing the carrier (*"Ci-joint les POD"*, *"peux-tu vérifier la quantité livrée"*), which meant the report was recommending customer-facing articles about internal logistics chasing. Internal senders are derived from `SUPPORT_MAILBOX`'s domain rather than hardcoded, with `INTERNAL_EMAIL_DOMAINS` for what config cannot imply — the 3PL at `deret.fr` is the one that matters here, while `nocibe.fr` and `sephora.fr` are genuine B2B retail customers and stay in. `--internal` reports on our own recurring threads instead (an ops-automation signal, not a knowledge-library one) and `--all-senders` restores the undifferentiated view. Net effect on the ranking: 4 of the top 8 "write this next" suggestions were internal threads; now none are. The same cap was also truncating **`embed:tickets`**, which matters more than the report: its redaction sweep clears vectors from redacted and soft-deleted messages, and past row 1000 it was not looking — derived personal data could have persisted indefinitely. It now considers all 1383 (0 stale, 0 to clear, so nothing had actually slipped through; the safety net was blind, not breached). `ticket_messages` is the only table past 1000 today — `tickets` at 565 is next, and its reader is already paged. The Shopify sync scripts read `customers`/`promotions`/`shopify_content_sources` unpaged to diff against Shopify; all are under 20 rows on the dev store, so they are latent rather than broken, and should move to `supabaseSelectAll` before a production catalog lands.
- **Forwarding non-customer mail to the right colleague (first Phase 4 tool, built — not yet run on live mail).** Some support mail is not support: a spontaneous job application, a Nocibé reorder PO, a partner's regulatory feedback. Nobody owes the sender a customer-service answer, so the resolution is that the person who owns that subject sees it. Measured, that is **38 of 330 customer-facing tickets (12%)** — careers 11, partner_collaboration 14, b2b 13 — closed with no order lookup and no drafted reply. **The rule is (`request_kind = 'contact'` AND the category has an address)**, and both halves are load-bearing: routing on category alone would divert genuine `b2b` reorder problems as FYIs, and the taxonomy already restricts `contact` to exactly those three subjects. Keyed per category rather than per `responsible_team`, because the team mapping sends `careers` to `contact` — the generic bucket the mail just came from. The covering note is in **French** — internal mail at a French company — and is built to avoid the two ways unattended French goes wrong: it never addresses the reader (the recipient may be a shared mailbox, so no tu/vous choice) and closes on `le message`, invariably masculine, rather than a pronoun that would have to agree with each category phrase. Sends through Graph's own `/forward`, so the recipient gets the original with attachments intact (a CV arrives as a CV) rather than a re-composition of the stripped `body_text` we store. Idempotent on `ticket_messages.id`, not the ticket, so a candidate's follow-up still reaches HR exactly once. Failures are `failed` rows rather than silence, and one bad address never stops the pass. Configured at `/settings`; a category with no address forwards nothing, which is the default for all 14. **Needs the `Mail.Send` Graph permission** — the only write this worker makes to Graph.
- **Running it for real found two bugs the tests could not.** The first live pass forwarded **0 of 42** — Exchange was mid-mailbox-move and every send returned `ErrorMailboxMoveInProgress`, a condition that clears itself in hours. Two defects surfaced from that. **Failures were not actually retryable:** the selection step excluded any message with a ledger row regardless of status, so 42 genuine emails were permanently locked out by a transient error — the exact opposite of the "visible and retryable" the migration comment claimed. Recording now upserts on `ticket_message_id` so a retry updates the row from `failed` to `sent`, and selection excludes only `sent`. **And the retry cap fought the poll interval:** a cap of 5 attempts against a 60-second poll would have burned every attempt in five minutes and abandoned the mail before the move finished. Transient Graph errors (mailbox move, throttling, 429/503) are now recorded but do not consume an attempt, so only a failure a human must fix — a wrong address, a revoked permission — counts towards the cap. **A third came from counting the real pending set:** 9 of 51 messages were from our own domain, colleagues forwarding things *into* the inbox with `TR:` subjects. `direction` only catches mail sent by the support mailbox itself, so a colleague writing from their own address is `inbound`; the audience split built for the clustering report is now applied here too. Net: 42 messages across 38 tickets, matching the measured figure exactly.
- **Knowledge retrieval (second Phase 4 tool, built and run against the real library).** One embedding call plus one HNSW-indexed `match_knowledge_chunks()` RPC returning a handful of rows — not a client-side scan, which is what PostgREST forces if you try to rank by `<=>` from the outside. The SQL returns cosine **similarity**, not raw distance, so every band in the codebase is on one scale. Three bands, not a boolean: **answerable ≥ 0.60, weak ≥ 0.45, otherwise nothing** — calibrated on the measurement that a genuinely correct match scored 0.62 while topics with *no article at all* still scored 0.38-0.48, because French support mail shares so much boilerplate that "not zero" means nothing. `answerable` follows the single best match rather than an average, so three vague chunks cannot outvote the absence of a real one, and below-floor chunks are dropped rather than ranked last (passing them as context invites the model to answer from them). Which categories to search is policy in `retrieval-rules.mjs`, not SQL — the ticket's own subject plus `faq`, because `faq` answers across subjects and, today, is the *only* category with any embedded content. **Measured on 12 real product/account tickets: 1 answerable, 8 weak, 3 nothing.** That is the library being empty, not the tool failing — the one hit was a newsletter question correctly matched to the newsletter FAQ at 0.72, and most weak matches land on one generic "conseils sur les produits" chunk that matches every product question at ~0.46-0.58. Retrieval is ready; it is waiting on the ~46 messages' worth of product content.
- **Product lookup and stock tools — specific product questions are answered from `products`, not from embeddings.** The knowledge library is the wrong place for "votre masque LED convient-il aux peaux sensibles ?": the ingredients, usage instructions and product FAQ already live on the product row. The only hard part is deciding *which* product, which is name matching, not semantic similarity — so the match runs on the **title column only**. Searching descriptions would be worse, since every anti-âge description mentions every other concern and the name is the distinguishing signal. Matching folds accents and typographic punctuation (`Source d’Eau` and `source d'eau` must reach the same tokens) and weights tokens by **IDF across the catalogue**, so `creme` (a third of titles) barely counts while `led` (one title) is nearly decisive — self-maintaining as the catalogue changes, where a synonym list would not be. **Ambiguity returns every candidate's full context, not a refusal:** "le coffret Caresse Temps Sublime" genuinely names two products, so both are handed over with a preamble stating that the exact product is not identifiable. Silently picking one is the dangerous case — the wrong ingredient list to someone asking about an allergy — but withholding both is merely unhelpful, and a reply can then either cover both or ask a question that already carries the information. The preamble is load-bearing: without it a model treats the first block as the answer and the second as extra detail, which is the silent pick one layer up. `product` is set only when there is a single answer, so a caller reading it cannot get a coin flip. The stock tool does the same for a couple of integers, where "one is in stock, the other is not" beats another round trip. Running it on real tickets caught a live failure — the `unlisted` sample *"Caresse Temps Sublime Nuit - échantillon"* beat the real €89.50 coffret at 0.88, because a short title is mostly covered by any question naming it; only `active` products are candidates now. **Two tools, not one with a flag:** a stock check returns one integer, not the ingredients and FAQ, because that is a few thousand wasted tokens on every availability question. Output is shaped into named sections (Description / Conseils d'utilisation / Ingrédients / Questions fréquentes), which required a **Shopify rich-text flattener** — `product_faqs[].answer` is a nested rich-text document stored as a JSON *string*, so unflattened a model receives 300 characters of escaped nodes where the answer should be. Stock reads `purchasable` rather than the raw count: Shopify allows overselling and one real row sits at **-1**.
- **Promotion tool: why a discount code is not working.** Targets the largest answerable topic left — 34 `promotions` tickets, 29 of them level 2, and the biggest single cluster in the whole inbox is the newsletter welcome code (20 messages). Resolves a code however it is typed (`qiriness10`, `QIRINESS 10`), suggests near-misses rather than silently matching them, extracts codes from message text against the real list so `URGENT` is never offered as a discount, and lists what is currently running. **The verdict is three-valued — `blocked` / `undetermined` / `eligible` — never a boolean.** Told `eligible: true`, a drafting agent will write *"votre code est valide, réessayez"* to someone whose basket is under a minimum nobody can see, and support has confirmed a falsehood in writing; so `eligible` is never claimed while anything is unknown, and the rendered output keeps **Cause identifiée** and **À vérifier avec le client** in separate sections, because merged into one list a model treats them alike. Settled outright: code exists, status, date window, usage limit, and — via the `on_email_marketing_list` generated column — whether an identified customer is actually subscribed. **The promotions sync was extended to make eligibility real:** `minimumRequirement`, `customerGets`, `customerBuys` and `customerSelection` were fetched as `__typename` only, so the snapshot recorded *that* a discount had a minimum but never what it was. It now stores thresholds, the products/collections a code is restricted to (with titles), and any customer-segment restriction — which turns "j'ai mis UKLED20 sur ma crème" from a shrug into *« Ce code ne s'applique qu'à : Masque LED Visage Éclat & Régénération »*. **The basket remains the one genuine blind spot:** there are no cart or checkout tables and Shopify's Admin API does not expose a live cart at all, so it is reported as unseeable rather than silently omitted — a check missing from the list reads as "fine".
- **Abandoned-checkout lookup — the partial answer to the basket blind spot (built, not yet validated).** Carts are not synced and the Admin API does not expose an in-progress cart, but `AbandonedCheckout` does: introspection against the live store confirms `discountCodes`, full `lineItems` with products and per-line discount allocations, and the price sets. Fetched **live per ticket, never synced** — abandoned checkouts are transient and carry a whole basket plus both addresses, so mirroring them would mean storing the shopping habits of everyone who ever bounced. Addresses are dropped on the way in. **The lookup is by date window plus a client-side email match**, because `abandonedCheckouts(query:)` supports only `default`/`created_at`/`email_state`/`id`/`recovery_state`/`status`/`updated_at` — there is no documented email filter, and a free-text `query:"<email>"` was accepted rather than rejected, which with zero rows in the store proves nothing. Paging is bounded so a support lookup cannot walk the entire history. **The payoff is that a recovered basket turns the promotion checks from statements into answers:** "il faut au moins 50 €" becomes "le panier est à 42,00 EUR, il manque 8,00 EUR", and "ce code ne s'applique qu'au Masque LED" becomes a decided pass or fail. A rule decided by the basket is never also stated as an unknown. Two things stay honest: the basket is dated in the wording (one from last Tuesday is not what the customer has now), and a code *absent* from `discountCodes` is reported rather than concluded from, since Shopify records applied codes and a rejected one may never appear at all.
- **Order-number resolver (built; verification proven, matching blocked on data).** The prerequisite for 172 of 330 customer-facing tickets (52% — order, delivery, payment, return), none of which can be answered until the ticket knows which order it is about; `shopify_order_number` was set on **0**. **Parsing is deliberately narrow:** `#4854` or `commande n° 3985` only, never a bare number, because French support mail is full of four-digit years, postcodes and prices and a wrong order number is worse than none. Counted over the corpus that is 1152 `#NNNN` plus 225 written-out forms. **The 911 `Q00 26200111` references are classified, not dropped** — they are internal ERP references that will never exist in `orders`, and failing to match one silently would look identical to "we cannot find your order" when the right reply is "that is an internal reference, could you give us the number beginning with #". **Verification is the point, not the lookup:** a number is written only when the order's `customer_email_hash` equals the ticket's `requester_email_hash` — both produced by the same `hashIdentifier`, so a match is proof without either side holding a raw address. **Proven end to end against real data:** `hashIdentifier(customer.email) === orders.customer_email_hash` is true for a real dev order, returning `confirmed` for its owner and `mismatch` for anyone else. **The name is part of the check, not a fallback.** Most people order and write in from the same address, so an email match is proof — but the legitimate exception is common: ordered from a personal address, wrote in from a work one. An earlier version refused to look at the name once the emails differed, which collapsed "someone else's order" and "same person, second address" into one flat rejection. Now a name agreement with a differing email is `name_match` — corroboration, not proof, never written automatically, and carrying `suggested_action: ask_purchase_email` so the next step is to ask the customer which address they purchased with. Only emails differing **and** names disagreeing is a `mismatch`. **No digit cap:** order numbers start around four digits and grow without limit, so a `{3,6}` bound would silently stop parsing once a store passed 999,999 orders. Length is not evidence — the parser needs a `#` or `commande` prefix and the **database decides** what is real, including reading the shop's actual `min`/`max` order number to say *"70853 is outside this shop's issued order numbers (1001-6300)"* rather than a flat "not found". **Measured on the corpus: 488 tickets, 139 with a parsed order number, 0 confirmed** — because the dev store holds orders `#1001`-`#1012` while the corpus quotes 101 distinct numbers from 302 to 70853. That is the data gap, not the resolver. **Validated end to end with a real-data fixture** — real dev orders and customers, real corpus email text with the number substituted, the real store querying Supabase, run dry: right owner → `confirmed`, someone else quoting the same order → `mismatch`, names-only → `name_only`, unknown number → `not_found`. That exercise also sharpened the range wording: it had been concluding a number outside the synced span was "likely not an order number at all", and said so about `#4009` — a real order, absent only because the dev store holds twelve rows. The margin is now proportionate, because `max` is always somewhat stale on a store that never stops selling: **far** above the newest order reads as a likely typo (the useful case), **just** above it reads as "too recent to have synced", and below the oldest reads as older than the ~6 months of orders retained.
- **Order-context bundle (built, verified on a real order).** The payload a drafting agent reads instead of querying fields one at a time, written to `tickets.resolved_context` once the resolver has CONFIRMED an order number — so a bundle can never be assembled for the wrong customer's order. **Derived, not copied.** The raw order carries four separate status columns, a fulfillments array and twenty monetary fields; answering "where is my parcel?" from that means the model deducing that `fulfillment_status = FULFILLED` with `delivered_at` and `in_transit_at` both null means "dispatched, no carrier scan yet" — a deduction it will get wrong, differently each time. So `delivery.state` is one of `not_dispatched | dispatched | in_transit | delivered`, computed the same way for every ticket, alongside a small set of signals that exist because a real cluster needs them: `awaitingCarrierScan` is the shape of the largest delivery topic (27 messages of *"je n'ai toujours pas reçu"*), and `isFullyRefunded` is separate from `isRefunded` because "you were refunded" reads very differently at 12 € of 89 €. **Personal data is scoped deliberately:** the buyer's name and email are carried, because support cannot answer without knowing whose order it is, but there is **no street address** (the sync stores only a coarse city/country) and **no phone** (this is an email desk). Tests assert both absences. Verified on the real `#1006`: a 1.7 KB bundle with tracking number, carrier, Colissimo link, `daysSinceDispatch: 17`, full-refund detection, and the customer's RFM group — and the pass links `tickets.customer_id` at the same time, so every later tool skips resolution entirely. A snapshot, with `--refresh` to rebuild after a sync moves the orders underneath.
- **Customer/CRM lookup (built, verified against the dev store) — the first tool that needs no order number.** The order-context bundle already carries a customer, but only ever reaches one by resolving an order, and only once that order is CONFIRMED. That left a class of ticket structurally unanswerable: the `account` questions ("combien de commandes ai-je passées ?", "je n'arrive pas à me connecter") have no order number to resolve and never will. This tool enters from the identity every ticket already has — the sender. **Two ways in, one bundle out:** `findByEmail` for a raw address, and `findByEmailHash` for `tickets.requester_email_hash`, which is all a ticket stores; the hash path means the ticket side never has to hold a raw address to ask a question about it. Since `customers.email` is plaintext and the ticket holds only a hash there is no column to join on, so the hash is computed on this side over an `id,email` index built **once per process, not once per ticket** — correct at any size, and the scaling fix when it is needed is a stored generated `email_hash` column, deliberately not a migration today. **The customer shaping was extracted, not copied:** `buildCustomerContext` now backs both this tool and `tickets.resolved_context.customer`, with a test asserting the two produce the identical object, because a second definition of "the customer bundle" would drift and silently change every context already stored. Account state is added only on the standalone side, and the distinction that earns its place is `INVITED` versus `ENABLED` — a customer who ordered but never activated the account is otherwise indistinguishable from a forgotten password, and the rendered text says *"le compte existe mais n'a jamais été activé"* rather than printing the enum a model would repeat verbatim. **The email is withheld from the prompt text by default:** the drafting step is replying *to* that address, so restating it adds a personal identifier to the model's context for no gain; the one question that needs it opts in explicitly, making the exception visible at the call site. **Every lookup writes a `data_access_events` row** with the customer id hashed — reading a customer to answer a ticket is access whether a human or the worker did it — and that write **fails open**, because by then the data has already been read and throwing would not un-read it, only also lose the answer. Runnable on its own: `npm run customer:lookup -- <email>`.
- **Quoted reply history is stripped before embedding and classification.** Measured on the real corpus, **104 of 348 messages carry a reply chain and it is 53% of the stored text** — over half the corpus was duplicated conversation. Re-embedding it made a follow-up nearly identical to the question it quoted, and it had the categoriser reading a quoted original as the thread's *latest* message. Every cut comes from an unambiguous structural marker (`De:`+`Envoyé:` block 88, `a écrit :` 10, `-----Message d'origine-----` 3, `From:`+`Sent:` 3); the loose `>`-line heuristic fires on none of them, and a wholly quoted message keeps its original body rather than stripping to nothing. The stripper version salts the message embedding hash, so changing it correctly invalidates every message vector.
- **Spam gate pass 2** — the LLM classifier (`gpt-4o-mini`, Structured Outputs) on new-conversation mail, which fails open on any error. **Run on real mail:** the first 100-message pass filtered 91 as spam, and inspection showed that was correct — the inbox is flooded with DMARC aggregate reports, which the classifier caught and explained in plain language. Adding the report senders to the blocklist moved them off the LLM path entirely (91-per-100 down to 27-per-500), since a deterministic domain match is free and instant where a model call is neither.
- **Categorising agent (agent Phase 3)** — a batch pass in the same poll that fills `category` + `request_kind` (plus the optional secondary pair), the derived `level`, and `responsible_team` on every open ticket still uncategorised. Classification only: no tools, no order lookup, and the prompt carries the subject and message bodies but never the sender's address or name. The Structured Outputs enums are generated from `support-taxonomy.mjs`, the level is clamped to the derived floor (including the secondary pair's), level 4 is reachable only by the severity escalation described above, and three failed attempts write (other, problem) → level 3 so the ticket reaches a human instead of retrying forever. **Run on real mail:** 171 tickets categorised across two passes with no failures and no fallbacks. Measured twice. Against 40 invented cases (`npm run eval:categorise`): ~38-39/40 on all three axes. Against **30 hand-labelled real emails** from `contact@qiriness.com` (`categorisation_review`, `npm run review:compare`): subject 70%, kind 93%, level 77% (re-scored 2026-07-27 after the review bodies were normalised to match what ingestion now stores; the previous 77/90/73 was measuring input the pipeline no longer produces). Those movements are 2 cases or fewer on n=30 and sit well inside the noise — the set is too small to resolve changes of that size, which is itself the finding. Five of the nine subject errors are the `order`/`delivery` boundary the plan expects Phase 4 order data to settle; four of the seven level errors are `delivery/problem` L3-vs-L2, where the human note each time reads "requires someone to intervene". Real mail is what drives the taxonomy now: the dispatch boundary between order and delivery, `complaint` only when nothing actionable is asked, `contact` only for a first approach, and the level floors all changed because human labelling disagreed with them.
- **Re-categorisation as threads grow** — a ticket's labels describe the conversation so far, not the email that opened it. Ingestion re-flags a ticket the moment a new *inbound* message joins the thread (never on our own replies), and the same batch pass re-reads it **blind** — the model is not shown its previous answer, which would only make it defend a first call that may have been wrong. A level may then rise but never fall (`ratchetLevel`), so an order question that becomes a lost parcel escalates, while a polite follow-up cannot walk a promised refund back out of the human queue. Superseded labels are kept in `metadata.categorisation.history`.
- **Two per-ticket signals** — read off the same email in the same call, since the model has already paid to read it. `language`, the language to reply in, restricted to what the desk can actually write (`other` routes to a human) — the drafting agent needs this before it writes a word, and on live mail it correctly caught 5 English, 1 Italian and 1 Spanish email among 163 French ones. `happiness` 1-4 (1 happy, 2 neutral, 3 discontent, 4 really unhappy: threatening to stop buying, calling it unacceptable, or chasing an unanswered thread). Happiness is **not** wired to `level` in either direction — level is what work a ticket needs, happiness is how the customer feels.
- **A third signal was built, measured, and removed.** The categoriser was also asked how confident it was. It answered `high` on 171 of 171 live tickets and 40 of 40 review cases: Structured Outputs emits fields in order, so the model was rating an answer it had already committed to in the same forward pass. The per-band accuracy report added to the eval is what caught it. The question was dropped rather than reworded — a constant field carries no information, and one called *confidence* invites the wrong decision downstream. `tickets.categorisation_confidence` survives as a known-untrustworthy marker written only by the failure paths. Until a calibrated signal exists (sampling for agreement, or token logprobs), Phase 5 should gate auto-drafting on `level` + `happiness`.

Not built: dashboard authentication, deployed webhook routes, and the agent's tool and drafting stages. 332 tests pass from the repo root (138 of them the `agent/` worker's). Backend/deploy config is still pending.

## Next Steps

Reordered 2026-07-30 after measuring the clustered corpus against the level taxonomy. The target is explicit: **auto-resolve level 1 and 2, and for level 3 assemble everything a human needs to act.** Across 330 customer-facing categorised tickets that splits **L1 42 (13%) · L2 156 (47%) · L3 131 (40%) · L4 1**, so 60% is in scope for automation and 40% for context assembly. What each tool is worth is in `AGENT_INTEGRATION_PLAN.md` Phase 4.

The previous ordering put the knowledge library first, on the reasoning that only one of nine documents is `approved`. That was measured and is wrong: embedding the 19 unapproved draft chunks of `Livraisons et retours` and `Conditions générales de ventes` in memory and scoring them against the top 12 customer topics closed **0** of them (best match for *"il me manque un produit"* is *"CGV / 9- Instructions pour l'exercice du droit de rétractation"* — contractual text answering an operational question). Approval was never the constraint. Roughly 127 messages of top demand need live order data and 46 need an article, so the tools layer is worth about three times the library.
